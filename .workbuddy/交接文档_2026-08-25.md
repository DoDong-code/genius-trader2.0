## 一、项目背景

项目：`genius-trader2.0`

核心功能：

* 基金持仓管理
* 基金实时估值
* 基金正式净值
* 基金历史净值
* 基金详情
* 多数据源切换
* Web
* 微信小程序 mp1
* 本地估值引擎
* 基金详情缓存
* PostgreSQL 云端数据
* 第三方数据 Provider

生产后端：

`genius-trader.onrender.com`

当前数据库：

PostgreSQL Cloud

## 二、近期最大的目标

最近几天主要围绕一个问题进行修改：

> **基金列表和详情中的“估值 / 正式净值 / 日期标识”混乱，同时历史净值更新不及时，切换数据源容易卡住。**

最终希望恢复到一个非常简单可靠的模型：

```text
正式净值
第三方正式 NAV
      ↓
fund_nav
      ↓
Web + 小程序
      ↓
蓝色 MMDD


盘中估值
第三方估值 / 本地估值引擎
      ↓
estimate
      ↓
灰色「估值」


没有数据
      ↓
不显示任何标签
```

## 三、最终 UI 规则

目前要求最终统一为三种内部状态，但 UI 只显示两种。

### 1. 正式确认净值

条件：

```text
nav.confirmed === true
AND
nav.date 存在
AND
nav.value > 0
```

显示：

```text
蓝色 MMDD
```

例如：

```text
0824
```

---

### 2. 盘中估值

条件：

```text
没有可用正式 NAV
AND
estimate.status === READY
```

显示：

```text
灰色「估值」
```

注意：

> 估值永远不能变成正式 NAV。

---

### 3. 没有数据

内部可以存在：

```text
NO_DATA
```

但 UI：

> **什么都不显示。**

禁止显示：

```text
暂无数据
数据异常
数据源
STALE
PROVIDER_TODAY
```

## 四、最重要的业务原则

### 正式 NAV 和 estimate 必须完全分离

正式 NAV：

```text
fund_nav
```

是正式净值唯一事实来源。

estimate：

```text
estimate
```

只是盘中估值。

禁止：

```text
estimate → fund_nav
estimate → confirmed
estimate → 蓝色日期
```

## 五、基金正式 NAV 数据链

当前设计：

```text
第三方正式净值
        ↓
navService / importFund
        ↓
fund_nav
        ↓
fundService
        ↓
/api/fund/:code
        ↓
FundStore / persistence
        ↓
Web / mp1
```

`fund_nav` 是正式净值事实。

数据库结构此前确认：

```text
fund_nav
```

核心数据：

* fund_code
* date
* nav
* acc_nav
* confirmed 等相关字段

历史数据通过 fund_nav 提供。

## 六、基金详情历史缓存

项目已经存在基金详情缓存结构。

近期明确要求：

> **不要删除基金详情缓存。**

当前目标：

```text
有缓存
 ↓
立即显示缓存
 ↓
后台增量更新
 ↓
新数据成功才替换
```

而不是：

```text
打开详情
 ↓
清空缓存
 ↓
重新请求
 ↓
等待
```

尤其不能出现：

```text
0824 缓存
 ↓
刷新
 ↓
后端只返回 0821
 ↓
把 0824 覆盖成 0821
```

因此历史数据必须遵守：

> **不能因为一次较旧响应而回退到更旧日期。**

## 七、近期出现的真实问题

目前生产实际出现过：

### 1. 基金日期混乱

例如持仓列表同时出现：

```text
0820
0821
0824
```

其中：

* 部分 QDII / 美股相关基金停在 0820
* 大量基金停在 0821
* 少数基金已经到 0824

这并不一定是 UI 问题。

必须首先确认：

> `fund_nav` 里到底有没有最新正式 NAV。

---

### 2. 大量基金缺 0824

生产真实测试曾发现：

例如：

```text
007339 → 0821
380006 → 0821
002207 → 0821
004253 → 0821
002910 → 0821
004103 → 0821
006503 → 0821
022184 → 0821
008702 → 0821
013309 → 0821
019633 → 0824
```

其中 `019633` 已经出现 0824。

这说明：

> 第三方数据本身并非完全没有 0824。

曾经的判断是：

> 生产缺少自动 NAV 全量同步机制。

但这个判断需要新的开发者重新验证。

## 八、曾经新增的 NAV 自动同步 Scheduler

近期在：

```text
server/index.js
```

增加过：

```text
startNavSyncScheduler()
```

设计：

```text
启动后 30 秒执行一次
之后每 4 小时执行
```

核心：

```text
navService.syncAll({})
```

目的：

> 自动把所有基金最新正式 NAV 同步进 fund_nav。

支持：

```text
DISABLE_NAV_SYNC=1
```

关闭。

## 九、Scheduler 当前存在严重疑点

部署后 Render 日志出现：

```text
[NAV-SYNC] scheduler started (interval=4h)
```

同时出现：

```text
ext(active=6,queued=165)
ext(active=6,queued=258)
ext(active=6,queued=277)
ext(active=6,queued=340)
ext(active=6,queued=351)
ext(active=6,queued=393)
```

也就是说：

> 外部 provider 请求队列持续增长。

因此：

**不能默认 `syncAll()` 是正确方案。**

它可能导致：

```text
syncAll
 ↓
大量基金
 ↓
大量第三方请求
 ↓
external queue
 ↓
provider 限流 / 超时
 ↓
NAV 仍然没有更新
 ↓
estimate 也受到影响
```

新的开发者必须重新检查：

```text
navService.syncAll
importFund
provider 请求队列
externalQueue
并发限制
```

确认它到底为什么会产生如此大的请求量。

## 十一、近期增加的 providerEstimate 超时护栏

文件：

```text
server/services/providerEstimate.js
```

近期增加：

```text
BULK_FETCH_TIMEOUT_MS = 8000
```

并增加：

```text
withBulkTimeout()
```

目的：

原来的 provider 底层请求可能：

```text
30 秒
```

而前端请求超时约：

```text
20 秒
```

于是出现：

```text
前端已经等待
 ↓
后端 provider 还没结束
 ↓
页面 loading
```

所以增加：

```text
8 秒整体护栏
```

希望：

```text
provider 超时
 ↓
reject
 ↓
本地估值引擎 fallback
```

但是这个方案也必须重新验证：

> 8 秒 timeout 是否真的能触发本地估值 fallback。

不能仅凭代码存在就认为有效。

## 二十七、最终期望架构

