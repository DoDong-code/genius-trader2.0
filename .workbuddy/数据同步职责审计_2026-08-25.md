## 一、当前实际调用链

### 1. 切换数据源（Web）

`status-clock.js applySourceSelection`
→ 写 `localStorage['estimate_source_<账户>']`
→ `triggerSourceRefresh({from,to})`（live-estimates.js）
→ 每个可见行 `fundDataService.refresh(code, true, { estimateOnly: true })`（persistence.js）
→ 只调 `estimateFund(code, amount)` → `GET /api/fund/:code/estimate?mode=provider&source=X`
→ `mergeFundData` 只合并 estimate 分支
→ `renderRowFromStore` 重渲染

**结论：切源目前只请求 /estimate，不请求 NAV/历史。** 唯一风险点：`triggerSourceRefresh` 缺失时的兜底会退化为 `refreshFundEstimates(true)`（全量 snapshot+estimate）。

### 2. 切换数据源（mp1）

`onSwitchEstimateSource` → 写 storage → `refreshData()` + `refreshEstimatesBySource(source)`
→ 每只基金 `GET /api/fund/:code/estimate?mode=provider&source=X`（并发 6）
→ 只更新 `today / todayEstimate / estimateSource / dataStatus`

**结论：mp1 切源也只刷估值。**

### 3. 刷新数据按钮（Web）

`status-clock.js` 刷新按钮
→ `refreshFundEstimates()`：每个可见行 `fundDataService.refresh(code, true)` =
  `GET /api/fund/:code?refresh=1&fast=1`（返回缓存 + 后台 `importFund`）
  + `GET /api/fund/:code/estimate`
→ `refreshMarketIndices()`
→ `refreshTodayNav()`：只取前 20 只 code 请求 `GET /api/fund/:code/today-nav?source=X`

**结论：一次刷新 ≈ N×（snapshot-fast + estimate）+ min(20,N)×today-nav + N×后台 importFund。** 违反「刷新不等于全量重拉」「必须覆盖全部持仓」「有今日 NAV 不重复请求」。

### 4. 刷新（mp1）

`refreshData()` → 用缓存建 navDateMap → `_refreshNavDatesIfNeeded(funds)`
→ 每只未标记今日更新的基金 `GET /api/fund/:code?fast=1`（纯读缓存，不触发 importFund，并发 6）

**结论：mp1 刷新较轻，但不检查今日 NAV 是否已发布（不调 today-nav）。**

### 5. 登录恢复（Web）

`persistence.js restoreCloud()`
→ `GET /api/account/state` → `applyAccounts`（云端覆盖本地）
→ `save()` → `PUT /api/account/state`
→ `refreshSyncedAccounts()` → `GET /api/portfolio/accounts`
→ `rerender` → `scan()` → 每行 `hydrateRow`
→ 有缓存先渲染，随后后台 `fundDataService.refresh(code, false)`（snapshot+estimate）

**结论：登录恢复 = 读云端状态 + 每只基金一次 snapshot-fast + estimate 静默请求。**

## 二、谁修改 NAV / Estimate / 清 FundStore

| 位置 | 修改内容 |
|------|----------|
| server `importFund` | 写 fund_nav（按 date upsert）、fund_holdings、fund 基本信息 |
| server `ensureTodayNav`（navCacheService） | provider 返回 expected 日有效净值且过 15:00 后写 fund_nav |
| server `/estimate` | 只返回 estimate（provider / local / 竞速），**不写 fund_nav** |
| Web `mergeFundData` | 合并 snapshot.latest_nav（设 confirmed=true）、estimate、history、detail、holdings |
| Web `refreshTodayNav` | /today-nav 返回有效净值才写 nav（value>0 守卫） |
| Web `fundDataService.refresh` | 只改 nav/estimate/todayProfit 的 status（REFRESHING/LOADING/ERROR），不清值 |
| mp1 `refreshEstimatesBySource` | 只改 today/todayEstimate/dataStatus |
| `restoreCloud` | 只替换 accounts（本地账户），FundStore 保留，**不清空** |

## 三、会造成 NAV 日期倒退 / 数据覆盖的点

1. `mergeFundData` 的 history 分支：`fund._history.data = snap.history` **无条件整体替换**，若响应历史比本地缓存旧，会把新日期覆盖成旧日期（违反「不能因一次较旧响应而回退」）。
2. `mergeFundData` 的 nav / estimate 分支：已有日期守卫（只允许 >= 缓存日期），不回退。
3. mp1 `navDateMap`：以当天服务器响应整体覆盖单只基金条目，若响应日期更旧会覆盖本地较新日期（仅影响当日 map）。
4. Web `getNavDisplayState`：**任何 confirmed NAV 都显示蓝色日期**，交易日「今日 NAV 未发布、最新 NAV=昨日」时仍显示蓝色昨日日期 —— 正是任务要消灭的「昨日净值蓝标」。
5. mp1 `getNavDisplayState`（tradingDay.js）：同样任何 confirmed NAV + date 都蓝，与 Web 一致地违反新规则。

## 四、ext 队列暴涨来源

`ensureTodayNav` 每只基金并发发起 2 个 `runExternal`（Yahoo + 天天基金），并发上限 6。
刷新按钮一次最多 20 只 → 峰值约 40 条队列；多标签/反复刷新/页面加载并发时队列累积（曾观测 queued=165~393）。
`navService.syncAll → importFund` 不经过 externalQueue，但会直连天天基金全量拉取，属于另一条 provider 压力来源。

## 五、结论与修改计划

1. 冻结三态：交易日 + 今日 NAV → 蓝今日日期；交易日 + 今日 NAV 未发布 → 灰「估值」；非交易日 → 蓝最近净值；无数据 → 留空。Web 与 mp1 统一。
2. 刷新按钮改为「增量检查当前账户全部基金」：已有今日 NAV 跳过；未发布则保留旧 NAV 并刷新今日估值；分批并发覆盖全部持仓，不调 snapshot 全量。
3. 切源保持 estimate-only，并移除全量兜底。
4. `mergeFundData` history 改为按日期合并、新日期优先，防止回退。
5. 新增后台每日 NAV 增量同步（跳过已有今日 NAV 的基金）、每周 35 天历史校对、每季度持仓检查；`navCacheService.js` 不动。
