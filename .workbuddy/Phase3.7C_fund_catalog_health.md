## 四、新增基金机制（静态代码分析，不涉及用户账户）

### 涉及文件与关键位置
- `server/services/portfolioService.js:19` `upsertFund(fundCode, fundName)`：仅 `INSERT fund(fund_code, fund_name, created_at, updated_at) ON CONFLICT DO UPDATE fund_name`。**只写名字，不写 NAV / history / holdings。**
- `portfolioService.js:41`：`upsertFund` 唯一调用点在 `replaceSyncedAccount`（**sync 账户导入流程**）的循环内 —— 即每一次账户同步都会为持仓基金建「名字行」，但**从不调用 `importFund`**。（`upsertFund` 另被 `module.exports` 导出，但全仓除 `replaceSyncedAccount` 内再无其它调用点。）
- `server/services/fundService.js:344` `importFund(code, options)`：真正补全基础数据 —— 写 `fund(fund_type, company)` + `fund_nav`(history) + `fund_holdings`。数据源为东方财富（marketService.collectFund）。
- `server/api/fund.js:704-713` `GET /api/fund/:code`：`getFund` 若返回 `null`（**无行**）才 `await importFund` 自动补全 —— **但若基金行已存在（如被 upsertFund 预建），该保护被绕过**。
- `fund.js:718-730`：`?refresh=1` / `?fast=1` 才显式触发 `importFund`（**写路径，本次禁用**）。
- `fund.js:554-561`：`/api/fund/import/:code` 显式导入端点。
- `server/services/estimateEngine.js:268-270`：估算时若 `getFund` 无 NAV，会 `importFund` 兜底（写入副作用）。
- `server/services/navService.js:37`：`importFund(fund.fund_code, options)` —— 已有**批量净值同步**逻辑（系统级扫表入口雏形）。
- `server/index.js:74`：启动时对 seed 清单 `importFund`（仅种子基金）。
- 注释 `portfolioService.js:4-5`：手动账户持仓保存在浏览器 localStorage，**不入服务端 `fund` 表**；仅 sync 账户（养基宝-/小倍养基-）经 `replaceSyncedAccount` 写入服务端。

### 当用户/系统第一次出现一个新基金代码时

1. **fund 表是否自动创建？** 是 —— 但只建「名字行」。sync 导入经 `upsertFund` 写入 `fund_code + fund_name`；手动账户不建服务端行。
2. **fund_name 是否自动写入？** 是 —— `upsertFund` 写 `fund_name`；`importFund` 也会从东方财富回填。
3. **importFund 是否自动触发？** **否（在 sync / 新增路径上不会）**。仅以下场景会触发：启动 seed(index.js:74)、`getFund` 无行时(fund.js:708)、`?refresh=1`/`?fast=1`(fund.js:721/725)、`/import/:code`(fund.js:556)、估算兜底(estimateEngine.js:269)、批量净值同步(navService.js:37)。**`upsertFund`/`replaceSyncedAccount` 本身不调 `importFund`。**
4. **fund_nav 是否自动填充？** 否 —— 仅 `importFund` 写入。
5. **fund_holdings 是否自动填充？** 否 —— 仅 `importFund` 写入。
6. **是否存在「只创建 fund 名称、没有 NAV/history/holdings」的情况？** **是，且这正是现状根因。** 本次 38 只 B 类基金的 `updated_at` 全部 = `2026-08-18T06:41:10`（sync `upsertFund` 批次时间戳），而 13 只 A 类 `updated_at` 各异且有 history —— 实证 sync 导入只建了名字行，`importFund` 从未为它们运行。

## 五、最终回答（6 问）

**问题1：当前 57 只系统基金中，到底有多少只基础数据完整？**
→ **13 只（22%）** 完整（A 类：NAV + history + holdings 齐全且未过期）。

**问题2：到底有多少只基金缺 NAV / history / holdings？**
→ 至少缺一项：**B(38) + D(5) = 43 只**（B 三项全缺、D 缺前十大）。若把「数据过期不可用」的 E(1) 也计入，则 **44 只（77%）** 基础数据不可用。C（有 NAV 无 history）= 0。

**问题3：为什么会出现「只有 fund 名称，没有 NAV/history/holdings」？**
→ 根因是 **`upsertFund`（`portfolioService.js:19`）只写 `fund_code + fund_name`**，被 `replaceSyncedAccount`（sync 账户导入）为每个持仓基金建「名字行」，但**不调用 `importFund`**；而 `getFund` 的自动补全保护（fund.js:708）只在「无行」时生效，名字行已存在 → 保护被绕过。结果：sync 导入的基金永远停在「名字行」，除非有人后续显式 refresh / import / 估算。本次 38 只 B 类的统一 `updated_at` 时间戳即铁证。

**问题4：以后用户新增一只基金时，系统能不能自动补齐基础数据？**
→ **当前不能。** sync 导入只建名字行；手动账户甚至不建服务端行。新增基金（无论来自现有用户加仓、新用户首次购买目录外基金、还是新 sync）都会复现同样的「名字行 / 空白」缺口。这是一个**系统性缺口，而非一次性的 26 只问题**——本次 38 只空白中，仅有 26 只被天才2.0/李总持有，另有 12 只空白基金根本不在这两个账户里，却同样损坏。

**问题5：如果不能，应该在哪个公共基金数据入口补，而不是针对某个用户补？**
→ 应在 **「基金代码首次进入系统 `fund` 表」这一公共事件**上补，与任何 user_id / 账户 / 持仓解耦。两条互补路径：
  - **(a) 写入即补全**：改造 `upsertFund`，当 `INSERT` 真正新建一个 `fund_code`（非 ON CONFLICT 更新）时，立即 `await importFund(code)`（可 fire-and-forget 异步）。这样「任何新基金代码出现 → 基础数据自动补齐」，天然覆盖未来新用户/新基金。
  - **(b) 系统级对账扫描**：复用 `navService.js:37` 已有的批量 `importFund` 能力，做成**定时任务**（如每日），扫 `fund` 表、对「缺 NAV/history/holdings 或过期」的基金补 `importFund`。这是真正的「基金基础数据同步机制」。
  - 保留 `getFund` 无行自动 import（fund.js:708）作为最后兜底懒加载。
→ 关键：**`fund / fund_nav / fund_holdings` 是公共基金基础数据层**，它的完整性不应由「某用户是否持有」决定。

**问题6：最终应该建立「基金基础数据同步机制」，而不是「用户持仓基金补数据机制」。**
→ 同意。Phase 3.7-B 设想的「按天才2.0+李总持仓补 26 只」是**治标**——它既会漏掉 12 只非两账户持有的空白基金，也无法覆盖未来新增基金/新用户。正确做法是建立**系统级、与用户解耦的基金基础数据同步机制**（问题5 的 a+b），让 `fund` 目录中的每一只基金都保证 NAV/history/holdings 完整。Phase 3.7-B 的 `--execute` 在此架构结论下**应暂停/不执行**——26 只缺口应由公共同步机制统一消弭，而非按账户手工补。

## 六、架构结论与下一步

- 现状：57 只目录中仅 13 只(23%) 完整，43~44 只基础数据缺失/过期，根因是 sync 导入只建名字行、缺公共补全入口。
- 修复方向（**待用户在下一阶段确认后才实施，本阶段不改代码**）：① `upsertFund` 新建行即 `importFund`；② 复用 `navService` 建定时对账扫描；③ 保留 `getFund` 懒加载兜底。
- 该机制上线后，目录内所有基金（含未来新增）自动补齐，mp1 详情页可直接读真实 NAV/历史/前十大，无需按用户补数、也不碰 mockHistory。

> 本阶段为**架构核验**，未执行任何生产数据写入（含 importFund / INSERT / UPDATE / DELETE）。完成后停止，等待确认。
